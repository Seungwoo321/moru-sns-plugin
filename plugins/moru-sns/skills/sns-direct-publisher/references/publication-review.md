# 형식 지원·후속 댓글·반응 관찰

## 현재 실행 범위

현행 `scripts/publisher.py`의 입력·검증·발행 경로를 기준으로 구분하라. 플랫폼 공식 지원은 이 CLI의 구현이나 현재 계정의 인증 완료를 뜻하지 않는다.

| 형식·작업 | 현행 CLI 범위 |
| --- | --- |
| Threads 텍스트 원글·개발 팁 | `--text-file` 원글 지원. 팁은 콘텐츠 구성 방식이며 별도 API 유형이 아님 |
| Threads 단일 영상 | 로컬 MP4 검증과 같은 파일의 공개 HTTPS URL로 지원 |
| Threads 본인 후속 댓글 | `--reply-to-job-id`가 가리키는 같은 계정의 저장된 published 원글에 텍스트 또는 단일 영상의 직계 후속만 지원. 댓글을 부모로 삼는 중첩 연속 글은 불가 |
| 이미지·여러 스크린샷·carousel | 현행 CLI에 이미지/children/carousel 입력·업로드·발행 경로 없음. 편집 후보로는 검토할 수 있지만 구현 완료로 보고하지 않음 |
| Instagram | Reels 캡션과 단일 영상만 지원. 기본은 공개 URL 방식이며 Unified에서만 명시적 resumable 로컬 업로드 가능. 사진 피드·carousel·댓글 발행은 불가 |
| X | 기존 텍스트·단일 영상 지원 유지. 현재 운영 정책이 연기한 연결이나 답글 기능은 추가하지 않음 |
| 반응 조회 | 저장된 published API 작업의 숫자 지표만. 댓글 내용·독자 질문·스냅샷 이력·게시 시각·형식을 자동 수집하지 않음 |

플랫폼에 가능한 미지원 형식은 현재 승인된 별도 도구·UI 경로의 계정·미디어·공개 범위·실행 가능성을 확인하거나 발행을 보류하라. 없는 CLI 옵션을 만들거나 스크린샷을 형식 지원 우회용 영상으로 자동 변환하지 마라. UI 게시물은 UI에서 확인한 사실·URL·시각과 실제 발행 경로를 운영 기록에 남겨라. API 발행 영수증이 없는 게시물을 위해 SQLite published 행을 합성하지 마라. 그런 게시물의 후속 댓글·지표 조회가 현재 CLI에서 가능하다고 약속하지 마라.

## 본인 후속 댓글의 대화·부분 실패 처리

- 원글은 단독으로 의미가 있게 완성하고 각 후속에는 재현 단계·세부 설명·한계 등 실질적인 추가 정보를 넣어라. 자기 댓글 수 자체를 조회 증가 수단으로 삼거나 한 이야기를 할당량 때문에 분할하지 마라.
- 공식 Threads API의 `reply_to_id`와 필요한 권한을 사용하되, 현행 도구는 저장된 자기 원글만 허용하는 더 좁은 범위를 유지한다. 타인 글·타인 댓글에 응답하지 마라. 현재 계정·원글의 대화 정책을 존중하고 API가 거절할 때 설정을 임의 완화하거나 다른 대화로 우회하지 마라. CLI가 `reply_control` 설정 기능을 제공한다고 말하지 마라.
- 준비한 원글과 각 후속의 내용·순서·개별 고정 job-id를 운영 기록에 구분하라. 원글 published 확인 후 각 후속을 순차 발행하며, 모든 후속은 같은 원글 job-id를 부모로 사용하라. 댓글의 성공을 다음 댓글의 부모로 바꾸지 마라.
- 각 단계의 성공 영수증을 확인하고 이미 성공한 원글·후속은 재발행하지 마라. 처리 중 항목이 있으면 그 항목의 기존 대기·재개 규칙을 따르고 다음 후속을 앞서 보내지 마라.
- 후속 하나가 실패·결과 불명이면 남은 후속을 멈추고 성공한 항목과 미완료 항목을 나누어 보고하라. 연속 글 전체가 원자적으로 성공하거나 되돌려진다고 설명하지 마라. 이미 성공한 원글·댓글을 삭제·재게시하거나 새 job-id로 잠금을 우회하지 마라. 원인·원격 결과·기존 기록을 대조한 뒤 지원되는 재개만 수행하라.
- 사용자 수정 금지 결정과 기존 첫 게시물을 보존하라. 새 편집 기준은 이후 게시물에 적용하라.

공식 기능 출처: https://developers.facebook.com/documentation/threads/retrieve-and-manage-replies/create-replies

## 반응 스냅샷

운영 정책의 점검 간격에 따라 실제 접근 가능한 게시물만 조회하라. 스크립트의 metrics 출력은 스냅샷 저장 기능이 아니므로 승인된 비공개 운영 기록에 아래 근거를 보존하라. 기록이 없으면 수집한 것처럼 이력을 만들지 마라.

| 기록 | 기준 |
| --- | --- |
| 게시물·플랫폼 | 실제 post ID/URL, 계정, 원글·후속 관계, 발행 경로(API/UI). 확인되지 않으면 unknown |
| 형식·맥락 | 텍스트·팁·원글/후속·스크린샷·영상 등 실제 형식과 주제. 플랫폼의 실제 미디어 유형과 편집 분류를 구분 |
| 게시 시각·경과 시간 | 실제 게시 시각과 출처, 관찰 시각·시간대, 계산 가능한 경우의 posted age. SQLite updated_at을 실제 게시 시각으로 대체하지 않음 |
| 관찰 값 | 지표 원래 이름·값·정의/범위·collected_at·조회 경로. UI와 API 값을 같은 출처의 연속 관찰인 것처럼 섞지 않음 |
| 조회 상태 | 성공/부분/미제공/오류와 확인한 제한·지연. 결측은 unknown/null로 보존하고 실패를 0으로 기록하지 않음 |
| 정성 반응 | 실제 읽은 질문·오해·재현 피드백의 짧은 요약과 출처·시각. 숫자 댓글 수만 확인했으면 내용은 미확인 |

현행 CLI의 Threads 지표는 `views`, `likes`, `replies`, `reposts`, `quotes`, `shares`이고 Instagram은 `views`, `reach`, `likes`, `comments`, `saved`, `shares`다. 공식 문서에 있는 시청 시간·스킵 비율 등 추가 지표가 이미 이 CLI에 구현됐다고 말하지 마라. 별도 승인된 조회 경로에서 실제 값을 얻었다면 출처·정의를 구분해 기록하라.

- API 영수증 없는 UI 게시물의 반응은 승인된 실제 조회 경로가 있을 때만 읽고, 없으면 현재 조회 불가로 남겨라. 댓글 본문 접근 권한·도구가 없으면 독자 질문을 추정하지 마라. 반응 관찰은 타인 댓글·DM 자동 발송을 허용하지 않는다.
- 누적 지표의 반복 스냅샷을 합산하지 마라. 같은 게시물·지표·정의·출처의 유효한 관찰끼리만 변화를 계산하라. 누락·조회 실패 시 이전 관찰을 덮어쓰거나 최신 값인 것처럼 재사용하지 마라.
- 플랫폼별 성과를 직접 비교하거나 합산한 순위를 만들지 마라. 같은 플랫폼에서도 주제·형식·게시 후 경과 시간이 다르면 그 차이를 표시하라. 원글과 후속 댓글의 조회를 더해 고유 독자 수로 보고하지 마라.
- 초기 게시 수가 적거나 비교 조건이 다르면 인과·최적 형식·알고리즘 효과를 단정하지 마라. 실제 질문과 반복 관찰을 다음 소재·설명·미디어 선택의 제한적인 근거로 사용하라. 반응이 낮다는 이유만으로 기존 게시물을 고치거나 삭제하지 마라.
- Instagram 공식 지표는 최대 48시간 지연될 수 있고, 존재하지 않거나 일시적으로 제공되지 않는 지표는 빈 데이터로 반환될 수 있다. 짧은 점검 간격이 실시간 확정값을 보장하지 않으므로 이 한계를 결과에 남겨라.

지표 한계 공식 출처(2026-11-22 확인): https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media/insights

## 정기 운영에서 연결

점검 주기·신규 자료의 누적 기간·발행 판단 시점은 운영 설정의 각각 다른 값으로 다루어라. 매 점검에 새로운 자료와 기존 게시 반응을 확인하되, 충분한 독립 소재·근거·공개 범위·실행 준비가 있을 때만 발행하라. 부족한 항목은 `sns-dev-stories`의 now/next 원천 피드백으로 넘기고 기존 요청과 스레드를 확인해 중복 요청하지 마라. 정시 보고 형식이나 SNS 문안 요구를 추가하지 마라. 구체적인 계정·주기·첫 게시물 URL은 이 스킬에 고정하지 마라.
