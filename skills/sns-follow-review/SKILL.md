# SNS 관심 계정 관리

현재 합의된 주제와 관련 있고 실제 작업·교류 근거가 있는 소수의 동료 계정을 신중하게 검토하라. 추천과 실제 SNS 관계 변경을 구분하고, 성장이나 노출 증가를 보장하지 마라.

## 범위와 자료 확인

- 운영자는 현재 사용자 요청 또는 승인된 정책이 지정한 주체를 따르고 특정 닷·대화로 고정하지 마라. ChatGPT가 운영자로 지정되면 승인된 하나의 SNS 정기 운영 작업 안에서 이 검토 절차를 사용할 수 있다. 개발 에이전트는 합의된 개발·녹화·원본 보고 제공 역할을 유지하며, 계정 검토·SNS 발행·지표 확인은 지정 운영자가 각 스킬의 허용 범위에서 조정한다. 별도 팔로우 실행 권한이나 두 번째 운영 작업을 만들지 마라.
- 현재 사용자가 지정한 SNS 계정, 관심 주제, 대상 목록·기간과 기존 사람의 결정을 우선 적용하라. 현재 사용자가 지정한 플랫폼과 우선순위를 따르고, 미연결 또는 이후 연결하기로 정한 플랫폼의 범위는 유지하라.
- [공식 조회 범위](references/official-data.md)를 읽고 현재 도구와 권한이 실제로 지원하는 조회만 수행하라. API 문서에 기능이 있다는 사실을 현재 계정에서 연결·구현됐다는 뜻으로 해석하지 마라.
- 사용자가 제공한 목록·내보내기·공개 링크를 먼저 사용하라. 공개 계정을 찾아달라는 요청에는 허용된 공개 검색을 사용하고, 연결된 공식 데이터는 현재 승인된 조회 범위에서만 사용하라. 로그인·권한·비공개 계정을 우회하거나 비공식 API·대량 스크래핑으로 명단을 복원하지 마라.
- 팔로워·팔로잉 **개수**를 계정 명단이나 관계 증거로 바꾸지 마라. 자동으로 전체 명단을 동기화한다고 보고하지 마라. 정확한 공개 핸들과 실제 근거를 확인할 수 없으면 대상 이름을 만들지 마라.
- 현재 사용 가능한 자료가 없으면 실제 후보 판단을 건너뛰고 필요한 계정 목록·내보내기·게시물 링크 중 최소한만 안내하라. 승인된 정기 작업에서도 자료가 없다는 사실을 기록하고 같은 자료 요청이나 가짜 후보를 반복 생성하지 마라. 연결되지 않은 계정에 접근했다고 주장하거나 빈 기록을 가짜 후보로 채우지 마라.
- 팔로우·팔로우 해제·좋아요·댓글·답글·DM·차단·신고를 실행하지 마라. 이 스킬을 추가했다고 기존 발행 스킬의 권한이나 기능을 확장하지 말고, 새 OAuth·메시징 권한·스케줄러를 구성하지 마라.

## 후보별 근거 수집

1. 플랫폼과 공개 핸들·프로필 링크를 정확히 맞춰라. 같은 이름의 다른 계정이나 다른 플랫폼 계정을 자동으로 합치지 마라.
2. 현재 관심 주제와 실제 게시물·작업 내용이 어떻게 관련되는지 기록하라. 프로필 자기소개만 확인했으면 그 한계를 표시하라.
3. 본인 글에 대한 구체적인 질문, 사용·재현 결과, 관련 경험 공유, 맥락 있는 피드백 등 **직접적인 의미 있는 교류**를 기록하라. 상대가 다른 사람과 한 대화를 우리 계정과의 교류로 바꾸지 마라. 좋아요 개수·짧은 인사·맞팔 요청만으로 관심이나 관계를 과장하지 마라.
4. 직접 작성한 글, 작업 과정·데모·수정 경과와 맥락 있는 대화 등 실제 활동의 공개 근거를 확인하라. 작성자의 자기보고와 직접 확인한 내용을 구분하고 게시 시각과 조회 시각을 따로 기록하라. "최근"이라고만 쓰지 말고 확인한 날짜를 제시하라.
5. `follows_me`와 `following_by_us`를 각각 확인하라. 사용자가 제공한 관계 목록·내보내기·확인된 공식 자료 등 직접 근거가 없으면 `unknown`으로 유지하라. 댓글을 달았거나 숫자가 늘었다는 이유로 맞팔이라고 추정하지 마라.
6. 조회 실패·부분 목록·비공개 전환·오래된 근거는 관찰 한계로 기록하라. 이를 봇·휴면·언팔로우의 증거로 바꾸지 마라.

## 판단 기준

- 실명·얼굴·아바타 유무·이름 형식·인증 배지·팔로워 수로 사람/봇 여부나 계정 가치를 점수화하지 마라. 실명이나 신분 증명을 요구하지 마라.
- 사람처럼 보이는 활동은 관찰일 뿐 운영 주체가 사람이라는 증명이 아니다. 자동화·AI 운영 여부는 공개된 자기설명과 확인 범위만 기록하고, 반응 패턴만으로 확정하지 마라.
- 직접 교류가 있는 관련 계정을 우선 검토하되, 새 계정처럼 교류 이력이 없는 상황에서는 주제·작업 근거가 있는 후보를 제한적으로 추천하고 "직접 교류 미확인"을 명시하라. 먼저 댓글이나 DM을 보내 근거를 만들지 마라.
- 맞팔하지 않음, 무응답, 게시 간격이나 일시적 비활동 **하나만으로** 팔로우 해제를 권하지 마라. 관련성·기존 관계·사용자의 선택을 함께 고려하라.
- 대량 팔로우/해제, 맞팔 거래, 수치 달성을 위한 반복 관계 변경을 권하지 마라. 공식 근거 없는 "안전한 하루 N명" 한도나 팔로우가 내 게시물 도달을 높인다는 인과 주장을 만들지 마라.
- 기존 사람이 정한 유지·제외·팔로우 관련 결정을 보존하라. 새 관찰과 충돌하면 새 근거를 검토 메모에 덧붙이고 기존 결정을 묵시적으로 뒤집지 마라.

| 결정 | 적용 기준 |
| --- | --- |
| `recommend` — 추천 | 주제와 실제 작업·활동의 근거가 있고 원하는 교류 맥락에 적합. 직접 교류 여부와 아직 팔로우하지 않았는지의 확인 상태를 구분하고 추천만 제시 |
| `keep` — 유지 | 현재 팔로우 또는 사용자의 유지 결정이 확인되고, 관련성·관계·선택을 유지할 근거가 있음. 잠시 활동이 없거나 맞팔이 아니어도 자동 제외하지 않음 |
| `review_unfollow` — 해제 검토 | 현재 팔로우 관계가 확인되고 사용자의 기준과 맞지 않는 구체적 내용·지속적 주제 변화 등 근거가 있음. 실제 해제는 수행하지 않으며 미확인 관계에는 이 결정을 쓰지 않음 |
| `hold` — 보류 | 계정 식별·관계·활동·관련성 근거가 부족하거나 서로 충돌함. 왜 판단을 보류했는지만 제시하고 사람/봇으로 단정하지 않음 |

## 기록과 출력

후보마다 다음 정보를 비공개 검토 기록으로 유지하라.

| 필드 | 기록 내용 |
| --- | --- |
| `platform`, `public_handle`, `profile_url` | 실제 자료에서 확인한 플랫폼·공개 핸들·프로필 링크. 확인하지 못한 링크는 `unknown` |
| `topical_relevance` | 현재 관심 주제와 맞는 구체적인 게시물·작업 근거 및 한계 |
| `meaningful_engagement` | 우리 계정과의 실제 교류 내용·대상 게시물·시각·출처. 없으면 관찰되지 않음 또는 `unknown`을 구분 |
| `original_activity` | 원작성 글·작업·대화 근거, 해당 게시 날짜와 확인 범위 |
| `follows_me`, `following_by_us` | 각각 `true` / `false` / `unknown`, 근거 출처와 그 관계를 확인한 시점 |
| `decision`, `reasons` | 위 네 결정 중 하나와 구체적인 근거·불확실성. 추천을 실행 완료로 표현하지 않음 |
| `sources`, `observed_at` | 주장별 공개 URL 또는 사용자 제공 자료 식별자, 자료 날짜, 실제 확인 시각·시간대 |
| `human_decision` | 사용자의 기존 결정·이유·날짜·출처를 보존. 새 추천과 실제 실행 상태를 별도 취급 |

- 관리 기록 유지가 요청되고 실제 후보 데이터가 있을 때만, 스킬 폴더 밖의 승인된 비공개 지속 저장 위치에 `follow_candidates` 운영 파일을 생성·갱신하라. 이미 있다면 먼저 읽고 같은 기록을 이어가라. 형식은 기존 JSON/표 형식을 우선 사용하라.
- 실제 자료가 없으면 운영 파일을 만들지 마라. 예시·가상 계정·테스트 데이터를 실제 후보 기록에 넣지 말고 스킬 자체에도 계정 목록을 고정하지 마라. 비밀값·비공개 메시지 원문·실명 추적 정보는 저장하지 마라.
- 같은 `(platform, public_handle)`의 중복을 합치되 이전 관찰과 사람의 결정을 지우지 마라. 핸들 변경이나 오래된 관계는 확인 없이 같은 사람의 최신 상태로 대체하지 마라.
- 응답은 계정·결정·핵심 근거·관계 확인 상태·출처·확인 날짜를 짧은 표로 보여 주어라. 부족한 후보 수를 채우지 말고, 실제 팔로우/해제/댓글은 수행하지 않았음을 명확히 하라.
- 이 스킬은 읽기 전용 판단 절차이며 SNS 관계 변경 실행기나 정기 동기화 작업이 아니다. 지정 운영자의 승인된 정기 작업에 포함돼도 읽기 전용 범위는 같다. 별도 실행 요청이 오더라도 현재 가능한 공식 기능을 확인한 뒤 판단 결과와 실행 가능 여부를 구분하라.
