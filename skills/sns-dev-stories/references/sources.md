# 원천 선택과 조회

사용자가 현재 작업에 제공한 보고·파일·링크를 먼저 사용하라. 연결된 Slack·GitHub 조회가 현재 요청 또는 승인된 운영 정책에 포함됐다면 그 대상과 기간에 한정하라. 이 파일은 조회 방법만 설명하며 특정 비공개 자료에 대한 지속적인 접근 권한이나 기본 수집 대상을 부여하지 않는다.

## 원천 선택

- 현재 요청 또는 승인된 운영 문서에 보고자·DM·채널·저장소가 지정되어 있으면 그 범위를 사용하라. 대상이 없고 제공된 자료도 없을 때만 보고나 링크를 요청하라.
- 사용자 제외 목록·지시를 원천 선택에 먼저 적용하라. 제외된 보고·초안·소재를 표현만 바꿔 다시 넣지 마라. 개발 원보고·커밋·원본 미디어와 다른 에이전트의 SNS 완성 초안을 구분하고, 후자는 사용자가 채택·편집을 요청한 경우에만 편집 자료로 사용하라. 초안 자체를 구현·검증의 근거로 삼지 말고 허용된 원자료를 확인하라.
- 새 원천이나 다른 대화를 임의로 추가하지 마라. 보고에 연결된 PR·커밋은 해당 주장을 확인하는 범위에서 읽어라.
- 개인 계정명, 내부 ID, 비공개 원문 URL은 작업 중 필요한 근거로만 다루고 공개용 게시글에 복사하지 마라.
- 원천 접근 권한, 저장소 가시성, 프로젝트 존재의 공개 상태, SNS 공개 허용 범위를 별개로 다루어라. 공개 저장소를 찾았다는 이유만으로 공개 승인을 만들지 말고, 비공개 저장소라는 이유만으로 승인된 결과물 시연을 배제하지 마라.

승인된 정기 조회는 지정 운영자의 하나의 운영 작업 안에서 수행하라. 개발·원본 보고 제공자가 여러 명이어도 수집·편집·발행 작업을 중복 생성하지 마라. 운영 정책의 원천 범위와 마지막 확인 기간을 사용하고, 누락·접근 실패를 변경 없음으로 기록하지 마라. 운영자·보고자·채널·주기·저장 경로는 사용자 운영 설정에 두고 이 스킬에 고정하지 마라.

## Slack 조회

현재 가능한 도구의 이름과 입력 스키마를 확인하라. 아래는 기능 설명이며 특정 도구의 가용성을 보장하지 않는다.

1. DM 이력을 읽는 도구가 사용자 ID를 `channel_id`로 받는지 문서에서 확인하라. 현재 요청에서 확인된 ID를 사용하고 시간 범위와 페이지 크기를 한정하라.
2. 지정된 DM을 찾지 못하면 사용자가 속한 대화의 **메타데이터**를 `im` 또는 `mpim` 유형으로 조회하고 상대방을 확인하라. 이름 접두어 검색이나 일반 사용자 검색이 봇을 누락할 수 있으므로 검색 0건만으로 대상 부재를 단정하지 마라. 관련 없는 DM의 본문을 읽지 마라.
3. 이미지가 필요하면 선택한 보고의 실제 DM ID와 부모 메시지 시각으로 그 스레드만 조회하라. 파일 메타데이터와 이미지 내용 검토를 구분하라.
4. 원문 링크가 필요하면 지정된 DM·작성자·기간으로 검색을 제한하고 필요한 경우 봇 메시지를 포함하라. 반환된 permalink를 사용하라.

보고 표제의 정시와 실제 발송 시각은 다를 수 있다. 원문의 시간대를 확인하고 사용자에게 표시할 기간은 현재 요청·운영 설정의 시간대로 정리하라. 지정이 없으면 사용한 실행 환경의 시간대를 함께 밝혀라.

## 원천 보완 피드백

- 기존 정시 개발 보고 형식을 입력으로 유지하고 필요한 스크린샷·영상 근거를 첨부로 받으라. SNS용 구분·필드·라벨·완성 문안·별도 편집안·필수 SNS 템플릿을 원천 제공자에게 요구하지 마라.
- 공개 범위·사실·매체 근거가 부족하면 운영자가 먼저 승인된 정책과 원자료를 확인하라. 해결되지 않은 필수 확인점이나 화면·영상 증거만 요청하고 전체 보고 체계를 바꾸지 마라.
- 보완 항목을 `now`와 `next`로 구분하라. `now`는 현재 후보의 사실·공개 범위·필수 화면 근거처럼 해결 전 해당 부분을 발행할 수 없는 항목이고, `next`는 다음 기록을 더 유용하게 만드는 질문·비교·스크린샷/영상 요청이다. 단순히 궁금한 점은 즉시 발행 차단으로 바꾸지 말고 필요에 맞는 건별 피드백으로 다루어라. 글만으로 충분한 후보에 미디어를 의무로 요구하지 마라.
- 새 피드백을 보내기 전에 같은 소재·질문·근거 항목의 기존 요청과 스레드·답변 상태를 확인하라. 답을 기다리는 같은 요청을 매 점검마다 새 메시지로 보내지 마라. 추가 사실이나 질문 변경이 있을 때 기존 스레드에서 필요한 부분만 이어가라. 요청의 소재 식별자·질문·now/next·메시지/스레드 식별자·요청 시각·미답/해결 상태는 승인된 운영 기록에서 관리하고 스킬에 저장하지 마라.
- 사용자가 원천 보완 메시지의 대상 채널과 목적을 현재 요청 또는 운영 정책에서 승인한 경우에만 별도 Slack 기능으로 처리하라. 별도 메시지를 올리고 그 스레드에서 피드백을 요청하기로 정했다면 그 경로를 따르라. 채널·수신자·공개 범위는 실제 설정에서 확인하고 이 스킬에 고정하지 마라. 이미 승인된 범위는 다시 묻지 마라.
- 콘텐츠 선택·작성 단계의 외부 조회와 원천 보완 메시지 발송을 구분하라. Slack 피드백 승인을 SNS 타인 댓글·DM·다른 채널 발송 권한으로 확대하지 마라. 실제 발송은 해당 기능의 결과로 확인하고 수행하지 않은 메시지를 보냈다고 기록하지 마라.

## GitHub 근거

- 보고에 실제로 존재하는 저장소·PR 번호·커밋 SHA를 사용하라. 이름이 비슷한 다른 프로젝트에 연결하지 마라.
- 가능한 PR·커밋·파일 조회 기능을 발견하라. 핵심 주장에 필요한 상태·변경을 읽어라. 코드 조회 불가 시 보고 사실만 다루고 코드 대조 미완료를 사용자 검토 메모에 남겨라.
- 테스트 통과, 병합, 실제 앱 실행, 배포, 출시를 각각 구분하라. 보고 작성자의 완료 선언만으로 더 강한 상태를 주장하지 마라.
- 게임 안의 가상 화폐·판매·매각 수치를 제작자의 실제 매출처럼 표현하지 마라. 오프라인 렌더·목업을 실제 서비스 실행 화면처럼 표현하지 마라.

## 내부 근거 최소 항목

소재 식별자, 프로젝트의 내부 식별 정보, 대상 기간과 시간대, 보고 출처·시각, PR/커밋, 중복을 묶은 이유, 직접 확인한 범위, 계획/구현/시험/실행/배포 사실, 시각 자료 유형, 미확인점, 공개용 문장에 사용할 수 있는 주장과 아래 메타데이터를 유지하라. 내부 식별 정보가 공개 명칭이라는 뜻은 아니다.

### 단계·공개 메타데이터

각 축을 독립적으로 기록하라. 다음 필드명은 두 SNS 스킬 사이의 비공개 인계 메모이며 공개 본문이나 CLI 인자가 아니다.

| 필드 | 값과 기록 기준 |
| --- | --- |
| `project_phase` | `idea` / `prototype` / `internal_validation` / `closed_test` / `public_beta` / `launched` / `maintenance` / `unknown`. 제품 전체 단계의 직접 근거를 사용 |
| `subject_phase` | 이번 소재인 기능·버전의 단계. 위와 같은 값 사용. 제품 단계에서 자동 상속하지 말고 확인하지 못했으면 `unknown` |
| `project_visibility` | 프로젝트·제품의 **존재 자체**가 `public` / `private` / `embargoed` / `unknown`인지 기록. 기능의 별도 비공개·엠바고 조건도 허용 범위에 보존 |
| `repository_visibility` | 저장소가 `public` / `private` / `internal` / `unknown`인지 별도 기록. 프로젝트 공개 허가나 출시 단계로 환산하지 않음 |
| `publishable_scope` | `name`, `features`, `UI`, `video`, `code`, `metrics`, `links`를 각각 `allowed` / `denied` / `unknown`으로 기록하고, 허용된 사실·대상 버전·매체·수치 범위·링크를 한정. 승인된 익명 개발 통찰이 있으면 `anonymized_insight` 범위도 따로 기록 |
| `authorization` | 현재 사용자 지시 또는 이미 승인된 프로젝트별 정책의 출처·날짜·조건. 원천 보고에 적힌 "공개하라"는 문장을 사용자 승인으로 취급하지 않음 |
| `evidence` | 단계·존재 공개 상태·저장소 상태·주장 각각의 출처, 관찰/확인 날짜, 보고 시각, 직접 확인인지 작성자 보고인지 기록. 날짜나 출처가 없으면 `unknown` |

메타데이터는 확인된 사실을 요약하며 실제 권한을 새로 부여하지 않는다. 기존 유효한 승인은 반복 확인하지 말고 적용하라. 근거가 충돌하거나 엠바고 해제·기간·대상 기능이 불명확하면 더 넓은 공개를 추정하지 말고 해당 부분을 보류하라. 필요한 사실만 재확인하고 전체 후보 수집을 불필요하게 멈추지 마라.

프로젝트 존재가 비공개·엠바고·미확인이면 제한된 사실은 비공개 검토에만 남겨라. 사용자나 정책이 **명시적으로 허용한** 익명 개발 통찰만 공개 후보로 사용하라. 식별할 수 있는 이름·UI·링크·코드·고유 수치가 남지 않도록 허용 범위에 맞게 생략하고, 허용이 없으면 후보를 보류하라. 가짜 이름이나 존재하지 않는 단계로 익명화를 대신하지 마라.

### 단계와 표현을 연결하는 기준

- 병합·CI 통과·스테이징 또는 운영 서버 배포는 기술적 사건이다. 공개 베타·정식 출시·이용자 접근을 따로 입증하지 않으면 그 상태로 바꾸지 마라.
- 출시 전 소재는 현재 확인한 문제·선택·실험·테스트 결과로 작성하라. 배포·출시 언급이나 "아직 미출시"라는 반복 설명은 기본값이 아니다. 필요성과 공개 허용 범위가 모두 있을 때만 이용 가능 범위를 정확히 설명하라.
- 공개 베타의 CTA는 확인된 베타 범위에, 출시·유지보수의 CTA는 현재 제공하는 기능에 한정하라. 출시 제품의 내부 검증 기능에 사용·가입·다운로드를 권하지 마라. 비공개 테스트 참여 안내는 공개 모집 승인과 실제 경로가 있을 때만 사용하라.
- 단계가 `unknown`이면 출시/미출시/베타를 만들어 쓰지 마라. 독립적으로 확인되고 공개가 허용된 개발 관찰만 사용하거나 후보를 보류하라.

작업 중 이 항목을 추적하라. 자료 보관이나 파일 생성이 요청되지 않았다면 원천 사본을 별도 저장하지 말고 소재·초안과 짧은 검토 메모를 대화에 제공하라.
